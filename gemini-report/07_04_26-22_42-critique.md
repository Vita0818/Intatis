目前 Intatis 最大的矛盾在于：**产品愿景是极具野心的“多 Agent 管理台”，但底层的架构实现和 UI 展现却依然带着浓浓的“传统单体 ChatBot”的残余。**

以下是基于源码暴露出的四大核心断层：

### 1. 团队协作的“信息灾难” (缺乏结构化上下文)
- **代码痛点**：在 `AgentLoop.swift` 的 `priorHistory()` 方法中，每次发起请求时依然在无脑**全量回放整个 `EventLog` 并将其转化为一维线性上下文**（`ConversationProjection.build(from: await log.replay())`）。
- **愿景断层**：如果你是在带一个多 Agent 团队，横向沟通和长链路的工具调用会产生海量噪音。全量拼接历史不仅会导致 Token 爆炸，更会让核心业务逻辑被淹没。
- **架构建议**：必须实现**结构化的上下文投影 (Context Projection)** 和**记忆分层**。Agent 间的通信应该只传递“核心摘要 (Summary)”和“工件快照 (Artifacts)”，而不是将整个群聊记录丢进单个 Prompt 里。

### 2. 汇报机制过于低级 (缺乏 Artifact 驱动的验收视图)
- **代码痛点**：在 `CodeViews.swift` 的 `CodeItemRow` 中，Agent 的代码修改 (`.patch`) 仅仅被渲染成聊天流中的一个纯文本卡片 (`card(icon: "doc.badge.gearshape", ...)`）。
- **愿景断层**：作为项目经理，你不需要盯着工程师敲每一行代码，你需要的是“验收成果”。当前的 UI 完全是“终端日志流”的思维，而不是“管理工作台”的思维。几十行代码的 Patch 以纯文本展示，管理者根本无法进行高维度的 Review。
- **架构建议**：UI 必须从“对话流驱动”升级为“**工件 (Artifact) 驱动**”。Agent 完成任务后，应该生成一份包含“修改动机、波及模块、测试状态”的结构化报告视图，并提供一个全局的“Approve / Merge”按钮，让用户体验到“我在验收产品”而不是“我在看日志”。

### 3. 被“圈禁”的虚拟员工 (缺乏自治执行闭环)
- **代码痛点**：`ShellGit.swift` 依然依赖于当前 GUI 主进程的 `Process()` 来执行 `/bin/sh`，且在沙盒环境下，`run_shell` 直接被 Permission Gate 封锁。Git 也只能看状态不能自动 Commit。
- **愿景断层**：一个无法自己编译、无法自己跑测试、无法自己提 PR 的虚拟工程师，是一个严重残疾的员工。沙盒机制让这套系统在真实项目中寸步难行。
- **架构建议**：必须彻底剥离出**独立的、跨进程的不受限执行 Daemon**，甚至为 Agent 团队打造一个**虚拟 CI/CD 沙盒环境**。Agent 应该能自动拉起 `make test`，消化错误输出并自我修复，直到最终交付可用成果给人类经理。

### 4. 授权网关体验断层 (缺乏宏观策略管控)
- **代码痛点**：`PermissionCard` 的设计要求用户对工具调用进行细碎的单次点击授权。
- **愿景断层**：当你雇佣了一个架构师，你不会要求他每次修改一个文件都来找你签字。这种高频的微观打断，彻底破坏了“挂机自动研发”的体验。
- **架构建议**：`PermissionEngine` 需要从“微观单次审批”演进为“**宏观策略签署 (Policy-based Access Control)**”。在任务开始时，用户签署一份租约（例如：允许本轮任务无限次读写 `src/ui`，但禁止修改 `Makefile`）。用宏观的边界限制取代微观的弹窗打断。
